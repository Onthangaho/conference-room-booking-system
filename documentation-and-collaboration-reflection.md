# Documentation and Collaboration Reflection

My original README assumed that readers already understood the background of the project and the Scrum framework. It mainly described the repository structure and technical details, without explaining what the system is, who it serves, or how someone new could contribute. This assumption made it difficult for a first-time contributor to understand the purpose and workflow without extra guidance.

The updated README improves onboarding by clearly outlining the system’s purpose, its high-level components, and how sprint documentation connects to the overall project. It now provides a roadmap for new developers, showing them where to begin, what artefacts are available, and how collaboration is managed through Pull Requests and issues. This structure reduces confusion, sets expectations early, and makes the repository more welcoming and professional.

Working with Pull Requests taught me that they are more than just code submissions. A good PR communicates intent, scope, and areas for review. Writing clear descriptions made me more deliberate in my decisions and helped reviewers provide focused feedback. Similarly, using structured issue templates highlighted how important clarity is in reporting bugs or proposing features. Well-documented issues reduce unnecessary back-and-forth and allow others to quickly understand and engage with the problem or idea.
